### 2. 그 실측 TAM의 **프레임 출처가 불확실하다** (사용자 지적, 2026-08-11)

위 TAM 이 실측 반영본이라는 것과, 그 실측이 **올바른 프레임에서 표현됐다**는 것은 별개다.
B1 측정의 라벨은 "뒤좌 CW", "앞좌 CCW" 같은 **사람의 시각 방향어**이고, 그 라벨은 "앞이
어디냐"에 의존한다. 그런데 그게 지금 미확정인 값(δ = 13° ± 10°, 아래 §5)이다.

행별 취약도가 다르다:

| 행 | yaw 프레임 회전에 영향 | 이유 |
|:---|:---|:---|
| Fz heave, **Mz yaw** | **없음** | z축 성분이라 yaw 회전 불변 |
| **Fx, Fy, Mx, My** | **있음** | 프레임이 δ 돌면 통째로 δ 돈다 |

수평 스러스터가 **45° 벡터드**라 45° 프레임 오차가 surge 와 sway 를 정확히 맞바꾼다.
IMU 오프셋도 45° 라서 혼동 가능성이 구조적으로 높다.

**해법: 측정을 사람의 프레임에서 떼어낸다.** Phase 0b 가 δ 를 확정하면 **팔이 IMU 프레임의
물리적 지시봉**이 된다. J1 을 알려진 각도에 고정하고 스러스터 방향을 "앞/뒤"가 아니라
**"팔 대비"** 로 기록하면, 사람의 방향 관념을 경유하지 않고 sim 프레임의 TAM 을 얻는다.
그래서 **Phase 0b 는 Phase 2 의 하드 선행조건**이다 (δ 없이 Phase 2 를 하면 같은 오염이 반복).

이 구조 덕분에 별도의 ε 보정항이 필요 없다 — `TAM_real` 을 처음부터 **IMU 보정 프레임에서**
재면, 아래 재매핑 `u_real = pinv(TAM_real) · TAM_sim · u_policy` 가 프레임 오차를 자동 흡수한다.

### 4. 지금 추력을 켜면 수직 모터가 수평 명령을 받는다 (**차단 결함**)

`thruster_mixer.py` 가 sim 이 이미 적용한 ESC 순열을 **두 번째로** 적용한다.

- sim: `ALBCThrusterCfg.allocation_matrix = _reorder_columns(_BASE_ALLOCATION_MATRIX,
  _ESC_CHANNEL_ORDER)` (`envs/main/config.py:144`). 즉 정책의 `action[2+j]` 는 이미 펌웨어
  채널 `mj` 용이다. 위 표의 Fz 행 `(1,0,0,1,0,0)` 이 그 증거 — 수직이 0·3번 열, 펌웨어 배선과 일치.
- 믹서: `DEFAULT_ORDER = [4,0,1,5,2,3]`, launch 기본값 동일 →
  **m0(수직) ← cmd[4](m4 수평용), m3(수직) ← cmd[5](m5 수평용), m1(수평) ← cmd[0](m0 수직용)**.
- 믹서의 안전 검증기 `_validate_order` 는 이걸 못 잡는다. `SIM_VERT = frozenset((4,5))`
  (`thruster_mixer.py:70`) 가 sim 재배열 **전** 인덱스라서다.
- 더 나쁜 방향: 올바른 값인 항등 `[0,1,2,3,4,5]` 를 넣으면 `{0,3} ⊄ {4,5}` 로
  **`ROSInitException` — 기동 거부**.

틀린 값은 통과하고 옳은 값은 거부된다. 지금까지 무해했던 유일한 이유는 `thruster_scale=0.0`
이었고, 이번 라운드가 그 방패를 내린다.

### 5. IMU 프레임 — 45° 상수는 검증됐고, 부호는 대수로 닫혔다

- 실측 46.9° vs 코드 상수 45.0° (1.9° 일치). 2026-08-11 팔을 지시봉 삼은 2방위 측정.
- `rotate_imu` + 방위 역산식의 합성 변환은 행렬식 −1 의 **반사** (`α_out = 135° − α_in`).
  두 측정에서 1.4°/0.8° 오차로 검증. raw 프레임이 좌수계이고 `raw_pitch = -(PITCH)` pin 이
  그것을 우수계로 되돌린다는 뜻.
- 보정 후 θ1=0 의 몸체 방위 δ: M1 → +3.5°, M2 → +23.2°. **δ = 13° ± 10°, ±180° 는 +x(앞)로
  갈렸다.** 단 이는 기존 원측정의 재분석이지 새 측정이 아니다 (Phase 0b 가 확증).
- vault 브리프 §3(d) 의 "축 이탈 3.3°" 는 M1 만 쓴 과신값. **δ = 13°±10° 로 정정한다.**

### 7. 스러스터 결속은 **클래식 PID 경로에만** 있다 — RL 경로는 이미 개별 제어

사용자 지적("여러개의 thruster가 묶여서 제어되는 것 같다 → 개별 제어로 펌웨어 수정을 배제하지 말자")을
펌웨어에서 확인했다. 결론: **RL 경로에는 펌웨어 수정이 필요 없다.**

| 경로 | 코드 | 개별 제어? |
|:---|:---|:---|
| ESC 와이어 프로토콜 | `thrusters.cpp:12` `esc_input(ID, pwm0, pwm1, pwm2)` — 보드당 3채널, ID 0x02/0x03 두 장 | **예** (6채널 독립) |
| **RL 믹서 경로** | `agent.ino:380,383` — `msg.thrust[0]`, `msg.thrust[3]` 을 각각 독립 기록 | **예** |
| **클래식 depth PID** | `pid.cpp:77-78` — `pwm_m0` 과 `pwm_m3` 에 **완전히 동일한 식** 대입 | **아니오 (결속)** |

`pid.cpp:77-78`:
```c
pwm_m0 = -PID_depth + ESC_NEUTRAL - DEPTH_BIAS;
pwm_m3 = -PID_depth + ESC_NEUTRAL - DEPTH_BIAS;
```

**이것이 2026-07-05 "m0·m3 같은 모터" 관측의 유력한 원인이다.** 그 측정이 클래식 depth 경로
(또는 teleop 의 depth 키)로 이뤄졌다면, 독립 2모터라도 같은 값을 받으므로 **무조건 하나처럼 보인다.**
따라서 §3 의 "수직 행 OPEN" 은 실제 배선 결손이 아니라 **측정 경로의 아티팩트일 수 있다.**
그렇다면 sim 의 수직 행 `Fz (1,0,0,1,...)` / `My (+0.145,...,−0.145,...)` 는 **맞는 것**이고
마지막 TAM 결손이 사라진다. Phase 2a 가 이걸 가른다 (아래 경로 규약 참조).

### 8. 클래식 PID 의 수평 allocation 이 내부 모순이다 (요구사항 "제어기 코드 수정" 의 답)

`pid.cpp:22-25` (정지 상태 yaw 제어):
```c
pwm_m1 =  PID_yaw + throttle + ESC_NEUTRAL;
pwm_m2 = -PID_yaw + throttle + ESC_NEUTRAL;
pwm_m4 = -PID_yaw - throttle + ESC_NEUTRAL;
pwm_m5 = -PID_yaw + throttle + ESC_NEUTRAL;   // m2 와 계수가 완전히 동일
```

yaw 계수가 `(+, −, −, −)` 로 **3-1 비대칭**이다. 4개 45° 벡터드 스러스터로 순수 yaw 를 내려면
2-2 여야 하고, sim TAM 의 Mz 행도 `(−, +, −, +)` 2-2 다. `m2` 와 `m5` 의 식이 글자 그대로
동일한 것은 복붙 오류의 전형적 형태다. throttle 계수도 `(+, +, −, +)` 로 같은 3-1 비대칭.

**영향**: 요구사항 R5 ("PID 제어기 기반 이동으로 로봇 프레임 검증")를 이 제어기로 그대로 하면
**제어기 자체의 결함이 프레임 판정으로 오독된다.** Phase 3a 전에 수정하거나, 아니면 Phase 3a 를
프레임 검증이 아닌 별도 목적으로 격하해야 한다. 이것이 요구사항이 예고한 "제어기 코드를
수정해야할 수도 있으므로 확인 필요" 의 구체적 답이다.

**주의**: 클래식 PID 는 실기에서 경험적으로 튜닝된 코드라 위 계수가 의도된 것일 가능성을 완전히
배제하지 못한다 (예: 고장 채널 보상). 코드 추론이므로 Phase 2b 의 단일 채널 실측이 상위 근거다.

## 재학습 판정: **하지 않는다**

근거 셋. 이전 감사의 근거("`thruster_scale=0` 이라 TAM 오류가 실기에 도달 못 함")는 사용자
결정으로 **폐기**됐고, 아래가 대체 근거다.

1. **최대 blocker 였던 수평 TAM 은 이미 닫혔다** (§1). 배포 모델이 실측 TAM 위에서 학습됐다.
2. **남은 결손(수직 행 + 프레임 출처 불확실)은 믹서 계층에서 흡수 가능하다.** 정책이 의도한
   wrench 를 `w = TAM_sim · u_policy` 로 재구성해 `u_real = pinv(TAM_real) · w` 로 내보내면

### 0k. 0d 실행 결과 — **게이트 불합격. `imu_yaw_offset` 이 180° 분기 반대편에 있다 (가설)**

2026-08-12 저녁, 전원·릴레이·`launch-agent` 인가 상태. `albc.launch` 로 TDC(`control_mode=1`)
구동, `rostopic echo -p /albc/status` 로 전 구간 기록(보드 `/tmp/0d_A_offset-78.csv`, 8148 행).
조작은 사용자, 기록은 세션 — 기울이면서 대시보드를 볼 수 없다는 제약에서 나온 분담이다.

#### 측정 (확정)

수평 기준선 roll +1.10 / pitch -0.17, J1 90.0° / J2 91.7°, EE target (-0.2330, +0.2323).

| 이벤트 | 구간 | 최대 기울기 | EE target 이동 |
|:---|:---|:---|:---|
| **3시 쪽을 아래로** | 26.8-35.9 s | **pitch -44.0**, roll -13.7 | `tx` -0.233 -> -0.408 (**-x = 9시**) |
| **12시 쪽을 아래로** | 57.3-76.8 s | **roll +29.0**, pitch +0.5 | `ty` +0.139 -> -0.392 (**-y = 6시**) |

교차항이 거의 0 이다 - roll 은 y 이동만, pitch 는 x 이동만 낳았다. **축이 섞이지 않았으므로
123° 잔차는 없고**, 남은 것은 통째 회전 하나다.

#### 부호 규약 대조 (확정)

프레임: **+x = 3시**(J1=0 tick 실측, IMU 무관), **+y = 12시**, **+z = 위**, 오른손.
각 축 둘레 양의 회전은 로봇의 "위" 벡터를 그 쪽으로 눕히고, 눕는 쪽이 내려간다 ->
**roll > 0 = 6시가 내려감**, **pitch > 0 = 3시가 내려감**.

이 규약은 세션의 유도가 아니라 **sim 이 쓰는 규약**이다 - `albc_env.py:703` 이
`euler_xyz_from_quat(root_quat_w)` 를 쓴다(표준 오른손 XYZ). 정책이 학습한 규약이 이것이다.
사용자도 같은 규약으로 조작했음을 확인했다("1번은 +pitch, 2번은 -roll 로 했다").

| 사용자가 한 것 | 규약이 요구하는 부호 | 실측 |
|:---|:---|---:|
| 3시 아래로 | pitch **양수** | **-44.0** |
| 12시 아래로 | roll **음수** | **+29.0** |

**두 성분 모두 반대다.** 2-벡터의 두 성분을 동시에 반전하는 것은 방위를 180° 돌리는 것과
같고, 그래서 팔이 낮은 쪽이 아니라 **높은 쪽**으로 갔다. 제어기는 `Fb = 13 N` 부력 EE 를
옮기는 모델(`albc_kinematics.h:15`)이므로 **낮은 쪽으로 가야** 수평이 된다 -> 종단 거동 반전.

#### 가설 (미확정 - 검증 대기)

`rotate_imu`(`build_proprio.py:107-113`, C++ 오라클 `imu_rotation.h`)에서 offset 은
`(raw_roll, raw_pitch)` 2-벡터의 **z-회전**이다. 따라서 **180° 를 더하면 두 성분이 동시에
뒤집혀 정확히 상쇄**된다 -> **`imu_yaw_offset: -78.0 -> +102.0`**.

부작용이 없는 이유: `out_yaw = YAW`, `out_r = GYRO_Z` 둘 다 **회전 없이 통과**한다
(`build_proprio.py:114`, `rotate_gyro` docstring). 즉 이 상수 하나가 자세와 각속도 p·q 만
뒤집고 yaw 추종은 안 건드린다. 자세와 각속도가 같은 상수를 쓰므로 프레임 정합도 유지된다.

⚠️ **§0g-4 의 "180° 분기 닫힘"과 모순되지 않는다.** 그것은 `J1 = +201° -> 팔이 8시` 관측으로
**몸체 프레임**(+x = 3시)을 못박은 것이고 IMU 를 쓰지 않았다. 여기서 뒤집힌 것은
**IMU -> 자세 부호**이며, 몸체 프레임은 그대로 유효하다. 서로 다른 사슬이다.

⚠️ **-78 의 출처가 같은 의심 대상이다.** -77.93 ± 4.8 은 2026-08-11 의 손 기울임 4방향을
수치적으로 푼 값이고, **같은 측정에서 나온 δ = -165° 는 이미 폐기됐다**. 기울임 방위 라벨이
계통적으로 180° 어긋났다면 회전각 적합은 정확히 -78 과 +102 사이에서 갈린다.

🔴 **가설이 맞다면 클래식뿐 아니라 정책도 영향을 받는다.** `rotate_imu` 는 **공유 사슬**이다
(RL 노드가 `albc_controller` 없이 도는 탓에 같은 보정을 자체 구현). 즉 배포 정책은 오전의
123° 를 고친 뒤에도 **180° 돌아간 자세**를 받고 있다는 뜻이 된다.

멈춰 세울 구조적 장치가 없다. 이론 최대 감김률 `0.10 × 1.0 × 50 Hz = 5 rad/s`.

## Phase 2 — 수 오전~오후, 수조 (3h) · **임계경로**

단일 채널 저출력 구동으로 `TAM_real` 의 **구조(부호·축)** 를 확정한다. 크기는 목표가 아니다 —
수조에는 IMU 와 depth 뿐이라 surge/sway 의 크기는 원리적으로 못 잰다
(omx wiki `sim_hydro_nominal_is_analytical_not_measured_imu_pressure_can_an`). 필요한 건 부호이고
그건 육안으로 충분하다.

### 관측 규약 — **"앞/뒤"가 아니라 "팔 대비"로 기록한다**

사용자 지적(§2)에 대한 구조적 대응이다. 매 측정 전에:

1. 팔을 **J1 = 0 tick** 에 토크 ON 으로 고정 (J2 = π/2 배포 자세 유지).
2. **팔의 몸체 방위 = J1 관절각 그대로다. δ 보정항은 사라졌다.**
   🔴 **2026-08-12 정정** — 여기 있던 "Phase 0b 가 확정한 δ" 는 **폐기된 값(−165°)** 이다.
   그 δ 는 `imu_yaw_offset = 45.0` 프레임에서 계산됐고, 그 프레임이 123° 틀린 것으로
   드러나며 함께 무효가 됐다(0f·0g). **폐기된 δ 로 2b 를 수행하면 모든 병진 방위가 165°
   회전된 채 기록되고, 오늘 반복해 겪은 대로 아무것도 에러를 내지 않는다.**
   대체: J1 Homing Offset `−1509` 이후 `J1 관절각 = sim 몸체 프레임 팔 방위` 가 성립한다
   (`J1 = 0 ⇒ link1 이 3시 = +x`, 90° 떨어진 두 점 측정 잔차 0.3°, 0h). 따라서 팔을
   **J1 = 0 tick** 에 두면 **δ = 0** 이고 규약이 한 단계 짧아진다.
3. 스러스터 반응을 **팔 대비 각도**로 기록한다 ("팔 방향에서 시계로 약 90°" 식).
4. **sim 프레임 방위 = 기록한 팔 대비 각도** (J1 = 0 일 때). J1 을 0 이 아닌 값에 두었다면
   그 관절각을 더한다. 사람의 "앞" 관념을 한 번도 경유하지 않는다.

yaw 반응은 IMU gyro z 로 직접 읽는다 (프레임 불변이라 이 규약이 필요 없음).

측정 순서는 위험도 순:

### 2a. 프레임 180° 판별 — ✅ **삭제됨. 0g-4 에서 건식으로 닫혔다 (2026-08-12 오전)**

여기 두 번 교체된 항목이다. 1차("m0·m3 이 같은 모터인가")는 0f 가 건식으로 답했고
(**다른 모터, m3(9시) 사망** → sim 의 독립 2채널 수직 모델이 맞고 `config.py` 의
"single-motor dual-ESC" OPEN 주석은 근거 상실), 2차(프레임 ±180°)는 **0g-4** 가 닫았다:
J1 이 예측하는 시계방향(8시 20분) vs 실관측(8시 근처) 대조로 `+x = 3시` 확정.

**수조에서 이 측정을 하지 말 것** — 물에 넣기 전에 이미 답이 나왔다. 30분을 2b 로 돌린다.

교훈(재발 방지): "물에서만 갈린다"고 적었지만 실제로는 **계기값이 예측하는 물리 방향을
눈으로 대조**하면 건식으로 갈렸다. 판별 실험을 설계하기 전에 *이미 가진 두 독립 계보가
서로를 검증하는지* 먼저 확인할 것.

**게이트**: 이 판정 전에는 `thruster_scale` 을 0.05 위로 올리지 말 것.

### 2a-old. m0·m3 이 같은 모터인가 — **해결됨, 기록용**

**경로 규약 (필수)**: 이 측정은 반드시 **RL 믹서 경로**(`/hero_agent/thruster_pwm` 로 직접 발행,
또는 `/albc/thruster_cmd` → 믹서)로 한다. **클래식 depth 키·teleop 으로 재면 안 된다** —
`pid.cpp:77-78` 이 m0·m3 에 같은 값을 넣으므로(§7) 독립 2모터라도 하나처럼 보이고, 그게 바로
2026-07-05 관측이 오염됐을 수 있는 경로다.

절차: m0 단독 구동 → depth 변화·기포 관찰. m3 단독 구동 → 동일. 그다음 m0=+, m3=− 차동 구동.

- **m0 단독과 m3 단독에서 서로 다른 위치의 프로펠러가 돈다** → 독립 2모터 확정.
- **차동에서 pitch 가 생기면** 독립 2모터 확증 → **sim 수직 행이 맞고 TAM 결손이 사라진다.**
- **차동에서 pitch 가 안 생기고 두 명령이 같은 프로펠러를 돌리면** 단일 모터 → 2d 의 수직 축소 규칙.

sim 최대 모멘트 팔(±0.145)이 전부 여기 걸려 있어 최우선이다.

### 2b-0. m0 부호를 **가장 먼저** 잰다 — m3 사망으로 위험이 한 채널에 몰렸다

남은 미측정은 `thruster_sign` 하나이고, **측정 순서가 안전을 가른다.** 수직이 둘이던
시절에는 한쪽 부호가 틀려도 heave 의 절반은 맞고 나머지는 pitch 로 샜다. **m3 가 죽은
지금 수직은 m0 하나뿐이라, 부호가 틀리면 heave 가 100 % 반대이고 맞설 모터가 없다.**
믹서도 기동 시 `THRUSTER SIGN TABLE IS IDENTITY (unmeasured)` 를 경고한다.

절차: `thruster_scale` 최저(0.05)에서 **m0 단독** → depth 부호 확인 → `~thruster_sign[0]`
확정. **이게 끝나기 전에는 수직 축을 쓰는 어떤 시험도 올리지 말 것.**

### 2b. 수평 4채널 — 부호와 **프레임** 동시 확인

m1·m2·m4·m5 각각 단독 저출력. 각 채널에 대해 기록:

- **yaw 방향** (IMU gyro z, 프레임 불변) → `TAM_sim` Mz 행 `(m1=−, m2=+, m4=−, m5=+)` 과 대조.
- **병진 방향** (위 관측 규약대로 팔 대비 각도) → `TAM_sim` 의 Fx/Fy 열과 대조.

**두 대조가 갈리는 것이 이 측정의 핵심이다.** yaw 는 맞는데 병진만 일관되게 어긋나면 그건
채널 오배정이 아니라 **프레임 회전**이고, 어긋난 각도가 곧 기존 B1 측정의 프레임 오차다.
그 경우 `TAM_real` 은 재측정 없이 `TAM_sim` 의 Fx/Fy·Mx/My 행을 그 각도만큼 회전시켜 얻는다:

```
[Fx']   [ cos ε   sin ε ] [Fx]
[Fy'] = [ −sin ε  cos ε ] [Fy]        (Mx, My 도 동일. Fz, Mz 는 불변)
```

### 2c. 고장 채널 확인 — ✅ **닫힘 (0f·0h, 건식). 수조에서 하지 말 것**

프롬프트 진술 "m3 간헐, m4 약함" 은 omx wiki 에서 근거 페이지를 찾지 못했고(query 3회),
**건식으로 이미 답이 나왔다**: `b1_channel_probe.py` 채널별 구동에서 **m4 는 정상**
("m4 약함" 진술 폐기), **m3(9시 수직)는 사망** — flash 후 정당한 문턱(0.15)에서
`+0.30 / −0.30 / +0.70` 전부 무반응으로 재확인(0h). 2a 에 이어 **두 번째로 수조 시간이
회수된다.**

⚠️ 정책은 fault-DR 로 학습됐으므로 중단 사유는 아니지만 **정상기 기준 판정은 금지**.
다만 커버리지의 실제 크기는 0i-3 을 볼 것 — "덮는다" 가 아니라 **"드물게 봤고, 암묵적으로만
식별한다"** 다 (특정 채널 사망 약 0.5 %/에피소드, `use_privileged_fault_obs: false`).

## Phase 3 — 수 오후, 수조 (2.5h)

### 3a. 클래식 제어기 동작 확인 (요구사항 R5) — ⚠️ **프레임 검증에서 격하 (2026-08-12 결정)**

**격하 근거 — 계수 문제가 아니라 구조 불일치다.** `pid.cpp:22-25` 를 실제로 읽으니 yaw
배분이 `m1 = +PID_yaw`, `m2 · m4 · m5 = −PID_yaw` 로 **3-1** 이다. 그런데 sim TAM 은 수평
넷의 `Mz` 가 **전부 +0.144** 로 같은 부호다. `throttle` 과 전후·좌우도 같은 3-1 패턴이라,
45° 캔트된 네 스러스터로 순수 병진을 만드는 **±± (2-2) 패턴이 아니다.** 계수 재튜닝으로
닫히는 종류가 아니고 배분 행렬을 다시 써야 하며, 그건 **재flash** 다 — 2026-07-03 에
flash 가 teleop 키 규약을 전면으로 깬 전례가 있다.

**그럴 필요가 없다**: RL 실기 경로는 `pid.cpp` 를 **전혀 쓰지 않고**(§7), 요구사항 R5 의
실질인 "사용자 프레임 ↔ sim 프레임 매핑" 은 Phase 2b 가 이미 닫는다. 따라서 이 단계는
프레임 판정 근거에서 빼고 **클래식 제어기가 살아 있는지 확인**하는 용도로만 둔다.
원래 서술대로 **결함 있는 제어기로 프레임을 판정하면 제어기 버그가 프레임 오류로
오독되므로**, 격하가 곧 그 위험의 회피다.

⚠️ 여기서 depth 를 쓰면 `pid.cpp:77-78` 이 **사망한 m3 에 계속 같은 명령을 넣는다** —
권한 절반 + 편심 pitch 가 섞이는 교란이다. **depth 를 판정 근거로 쓰지 말 것.**

#### 클래식 제어기 검증 체크리스트 (2026-08-12 추가)

오늘 변경 중 **클래식에 닿는 것은 `imu_yaw_offset` 하나뿐**이다 — `thruster_order` 순열과
믹서 불감대 보상은 RL 전용이고, `pid.cpp` 는 **믹서를 거치지 않고** `pwm_m0..m5` 를 직접
쓴다. 펌웨어 6채널 span 300·bias 0 통일도 **RL 콜백에만** 적용됐다. 그래서 넷을 따로 판정한다.

| # | 대상 | 어디서 | 선행 조건 | 판정 |
|:---|:---|:---|:---|:---|
| 1 | **자세 (TDC, 팔 전용)** | **0d 건식** → Phase 1 습식 | 없음 | 팔이 부력 높은 쪽을 올리는 방향으로 가는가. **123° 정정 후 첫 검증**이라, 이상하면 부호가 아니라 **게인**도 의심할 것 |
| 2 | **yaw** | 3a, 저출력 | 없음 — `acc_yaw` 는 보드 내부(`ahrs.cpp:71`)이고 z 축이라 회전 불변 | 도는가, 의도한 방향인가. 배분 3-1 은 sim TAM 과 다르지만 클래식은 sim TAM 을 참조하지 않으므로 그 자체가 결함은 아니다 |
| 3 | **앞뒤좌우** | 3a | 🔴 **Phase 2b 필수** | sim 기하(대각 45° 캔트)는 순수 병진에 **2-2** 패턴을 함의하는데 `pid.cpp` 전진은 `m1 +, m2 −, m4 +, m5 +` 로 **3-1** 이다. 어느 쪽이 실물인지는 미측정 `thruster_sign` 이 정한다 — **2b 전에 계수를 고치면 근거 없이 고치는 것** |
| 4 | **depth** | 3a, **생존 확인만** | — | 🔴 **판정 근거로 쓰지 말 것.** m3 사망이 섞여 "제어기가 나쁘다" 와 "모터가 없다" 를 구분할 수 없다 |

**펌웨어에 roll/pitch PID 는 없다**(`pid.cpp` 에는 `PID_control_yaw` 와 `PID_control_depth`
둘뿐) → 자세는 **원래부터 팔 전용**이고, m3 사망으로 pitch 의 스러스터 권한까지 사라져 실질
arm-only 다. 3 번이 2b 를 기다리는 덕에 **수조 단일 채널 측정 하나가 RL 과 클래식을 동시에
판정한다** — 따로 실험을 세울 필요가 없다.
경로 분리의 전모는 auto-memory `project_albc_classic_vs_rl_path_split` 참조.

전진·후진·좌·우 명령에 로봇이 사용자가 생각하는 방향으로 가는지. **이건 사용자 프레임과
sim 프레임의 관계를 확정하는 측정이지 성능 시험이 아니다.** Phase 2b 가 sim 프레임을 이미
닫았으므로, 여기서 어긋나는 각도가 곧 **사용자 프레임 ↔ sim 프레임 오프셋**이고 이는 문서로
남기면 되는 값이지 고칠 대상이 아니다 (조종자 직관용 매핑).

### 3b. RL 정책 — 추력 단계 상승

`thruster_scale` 을 **0 → 0.05 → 0.1 → 0.3** 으로 올린다. 각 단계에서 near-level 시작,
`thruster_max_s` 로 시간 제한, `/albc/thruster_cmd` 와 `/hero_agent/thruster_pwm` 동시 녹화
(fieldtest launch 가 이미 자동 rosbag).

### 3c. 판정 — **기준이 두 개로 갈린다**

과거 fieldtest 봉지는 전부 추력 0 이었으므로 (§6):

| 구간 | 판정 종류 | 기준 |
|:---|:---|:---|
| `scale = 0` | **회귀 부재** (과거 기준선과 비교 가능) | 관절 목표 폭주 없음, near-level 발산 없음, 포화율 비교 |
| `scale > 0` | **신규 안전** (비교 대상 없음) | 발산 없음, 의도 방향으로 움직임, 포화 없음, 수직 채널 오작동 없음 |

이 구분을 안 하면 스러스터 ON 에서 성능이 나빠진 것을 "회귀"로 오독한다. 기존 세션 프롬프트의
"성능 향상이 아니라 회귀 부재" 기준은 `scale = 0` 구간에만 적용된다.

## 불변식 (어기면 사고)

- 토크 켜기 전 **Goal Position 을 현재 위치로 덮어쓸 것**. `prof_vel = 0` 은 정지가 아니라
  **최고속 무제한** — 움직이기 전 20 으로.
- 로봇 상태를 바꾸는 조작(릴레이 ON, 추력 인가, 코드 배포, EEPROM 쓰기)은 **실행 전 사용자 확인.**
- 실기 실측이 코드·문서와 어긋나면 **실측이 이긴다.** 어긋난 지점은 그 자리에서 기록.
- 확인 안 한 것을 단정하지 말 것. 이 감사에서도 stale 컨테이너를 읽고 TAM 을 오판했다가 정정했다.
