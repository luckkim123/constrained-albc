## 1. What the tutorial implements, cell by cell

| Cell | Type | Content |
|---|---|---|
| 0–1 | md | Colab badge; states the demo covers a **single** system: differential-drive robot (DD-R) |
| 2 | code | Imports: `numpy`, `matplotlib.pyplot`, `scipy.linalg.{pinv,eig,solve_discrete_are}`, `scipy.linalg` (as `linalg`), `time`. Fixes `np.random.seed(0)`. |
| 3–4 | md/code | Defines state/input choice: `x=[x_pos,y_pos,theta]` (3D), `u=[v,omega]` (2D). Ground-truth dynamics are **hand-coded unicycle kinematics**, `f_continuous`/`f_discrete` (Euler, `dt=0.05`) — i.e. the "robot" is a closed-form ODE, not a simulator or hardware. |
| 5–6 | md/code | Data collection: 200 short trajectories × 50 steps = **10,000 (state,input,next-state) triples**, generated by rolling `f_discrete` forward from random initial poses with a piecewise-random input (95% uniform-in-range + Gaussian jitter, 5% larger "burst" pulses) for persistent excitation. All stored as plain `X,Y,U` numpy arrays of shape `(3,10000)`/`(2,10000)`, built via a Python double `for` loop (not vectorized). |
| 7–8 | md/code | `Lifting` class = the dictionary of observables. Config knobs: `poly_order`, `use_trig`, `include_u_in_phi`, `cross_terms`. `phi(x,u)` concatenates: identity terms `x`, monomials up to `poly_order` (brute-force recursive enumeration, duplicates the identity terms when `poly_order=1`), `[cos(theta), sin(theta)]` if `use_trig`, pairwise cross terms `x_i*x_j` if `cross_terms`, and optionally raw `u` + `u`, `u**2` if `include_u_in_phi`. Two example configs print dims **17** (no `u`) and **28** (`u` included). |
| 9–10 | md/code | **EDMD regression.** Actual lifting used for the model: `Lifting(poly_order=1, use_trig=True, include_u_in_phi=False, cross_terms=True)` → **11-D dictionary** = `[x,y,theta]` + duplicate degree-1 monomials `[x,y,theta]` + `[cos θ, sin θ]` + 3 cross terms `(xy, xθ, yθ)`. Builds `PhiX`, `PhiY` (11×10000), stacks `Z=[PhiX;U]` (13×10000), solves `K_edmd = PhiY @ pinv(Z)` — a single batch **least-squares pseudoinverse**, no regularization, no iterative solver. Splits `K_edmd` into `K_phi` (11×11, autonomous dynamics) and `K_u` (11×2, input-affine gain) — this is the "affine input form," Eq. (13)-style in the paper, **not** the joint-lifting form the `Lifting` class also supports via `include_u_in_phi`. |
| 11 | code | Linear **decoder** `C = X @ pinv(PhiX)` (3×11) maps lifted state back to original state; reconstruction RMS error on training data ≈ 0.00000 (near-exact, expected since `phi` is a superset containing the identity map). |
| 12 | code | Open-loop rollout check: 6 random 30-step segments, propagate `phi_{t+1} = K_phi·phi_t + K_u·u_t`, decode with `C`, compare vs. ground truth. Mean final-step error ≈ **0.0157**. Plots per-test error curves (log-scale) + one xy trajectory overlay. |
| 13–14 | md/code | **Koopman MPC.** `A_l=K_phi`, `B_l=K_u`. Builds a sinusoidal reference path (400 steps, `dt=0.1`), lifts it (`Phi_ref`), then runs a **receding-horizon QP via `cvxpy`** (horizon `N_mpc=15`, quadratic cost on lifted-state tracking error + input effort, box input constraints `u∈[-1.5,1.5]×[-5,5]`), solving a fresh `cp.Problem` **every one of 400 steps** and applying only the first control (closed-loop, but true dynamics are `f_discrete`, not `K`). Reported total execution time: **37.955 s** for 400 sequential CVXPY solves (~95 ms/step) — single trajectory, single CPU thread, no batching. Plots: xy tracking overlay, tracking-error-vs-time, `v`/`omega` command histories.

No LQR is actually built despite `eig` and `solve_discrete_are` being imported in cell 2 — both are unused in the notebook (dead imports). Control design is MPC-only, via `cvxpy`.

## 2. Libraries and GPU/torch readiness

Actually imported and used: `numpy`, `matplotlib`, `scipy.linalg.pinv`, `cvxpy` (+ its default solver, falls back to `cp.OSQP` on exception), `time`, `itertools.combinations_with_replacement`.

Not used despite being name-dropped: **PyTorch — never imported, never used.** **scikit-learn — never imported.** **PyKoopman — never imported**; it is mentioned only in the README's "Recommended Further Reading" list as an external, more advanced alternative the authors point to instead of building it in. `scipy.linalg.eig`/`solve_discrete_are` are imported but dead code.

Everything is **CPU-only NumPy/SciPy** with a **CVXPY convex-solver** in the loop. There is no `torch.Tensor`, no `nn.Module`, no autograd, no batch/vmap dimension anywhere. Nothing here is GPU-ready or torch-ready as written — the whole pipeline is single-precision-agnostic Python/NumPy list-and-loop code the README itself calls "intentionally simple and not optimized for performance."

## 3. What is reusable for a PyTorch + Isaac Lab RL pipeline (4096 parallel envs, GPU obs tensors) — and what is not

**Reusable (concept/algorithm-level, requires re-implementation, not code copy-paste):**
- The **EDMD closed-form regression** `K = Φ(Y)·Φ(X)^+` (cell 10) is a linear-algebra idea trivially portable to `torch.linalg.lstsq`/`torch.pinverse` and batchable across a state-transition buffer — this is the one piece with a direct, mechanical GPU port.
- The **affine-input decomposition** `K_phi`/`K_u` (state-autonomous vs. input-driven halves of the operator) is a clean design pattern worth keeping conceptually.
- The **dictionary-design taxonomy** (polynomial + trig + cross terms, `include_u_in_phi` toggle) is useful as a checklist of what "lifting" choices exist, not as production code (see §1's note on the duplicate-identity bug at `poly_order=1`).

**Not reusable, and not a small gap:**
- **Offline, single-trajectory, CPU least-squares fit of one global, time-invariant `K` for one fixed 3-DOF known dynamical system.** There is no notion of parallel environments, no batch dimension, no per-environment or per-episode variation of dynamics (no domain randomization, no privileged parameters distinct from state) anywhere in this notebook.
- **CVXPY-in-the-loop MPC**, one `cp.Problem().solve()` per timestep (400 sequential solves, ~95 ms each, 38 s wall-clock total) is architecturally incompatible with a per-step RL policy `forward()` call across 4096 parallel envs on GPU — it is not differentiable, not batched, and orders of magnitude too slow (an RL policy forward pass needs to run in well under a millisecond across all 4096 envs combined, not ~95 ms for one).
- **No neural network anywhere.** The tutorial explicitly declines to implement NN-based lifting ("For simplicity, we didn't include the NN-based construction here but you can refer to our another work (K-RSR)..." — markdown cell 7), which is precisely the piece an RL encoder/policy integration would need.
- **The lifted dictionary is fit to, and only valid for, the fixed ground-truth kinematics `f_discrete`.** There is no mechanism in this code for a `K` that is conditioned on unknown/randomized plant parameters (currents, thruster faults, hydrodynamic coefficients) — those don't exist as a concept in this system.

## 4. Gap assessment: this code vs. "lift a 72D obs vector inside an RL policy forward pass"

The distance is large and categorical, not incremental:

1. **Fit regime**: tutorial fits one 11×11 `K` once, offline, from 10,000 pre-collected samples of a *known*, *fixed* 3-DOF system via a single `pinv` call. An RL forward pass needs either (a) a **fixed, pre-trained** lifting+operator applied per-step at inference speed (feasible, but nothing here shows how to train `K`/`Φ` jointly with a policy via backprop — EDMD's `pinv` solve is not a differentiable-training-loop primitive as used here), or (b) an **online-adapted** operator, which the tutorial never demonstrates (no online/recursive EDMD variant, no time-varying `K`).
2. **Dimensionality and system class**: the demo lifts a 3-state, 2-input kinematic unicycle to 11-D. Scaling the identical polynomial+trig+cross-term dictionary construction to a 72-D policy-obs / 28–34-D privileged-obs UUV+arm system is combinatorially unfavorable (cross terms alone are O(n²); polynomial terms are O(n^order)) and there is no evidence in the tutorial that such dictionaries stay well-conditioned or Koopman-invariant at that scale — see §6 for why the paper itself flags this as unresolved.
3. **No batching, no GPU, no differentiability, no integration with an actor-critic or an encoder/policy `nn.Module` stack anywhere in the 409 lines.** Every architectural assumption of the Isaac Lab pipeline (4096 parallel envs, tensorized obs, backprop through the encoder into the policy, TRPO/IPO trust-region updates) is absent from this code.
4. What *is* directly transferable is the **regression formula and the affine-input factorization pattern** — a re-implementation from scratch in `torch`, not a port.

EDMD fit — the whole model-identification step (cell 10):
```python
lifting = Lifting(poly_order=1, use_trig=True, include_u_in_phi=False, cross_terms=True)
PhiX = np.vstack([lifting.phi(X[:,i]) for i in range(M)]).T
PhiY = np.vstack([lifting.phi(Y[:,i]) for i in range(M)]).T
Z = np.vstack([PhiX, U])
K_edmd = PhiY.dot(pinv(Z))
K_phi = K_edmd[:, :N_phi]; K_u = K_edmd[:, N_phi:]
# -> Estimated K_phi shape: (11, 11), K_u shape: (11, 2)
```

```python
for t in range(H):
```

## 6. Assessment of the two proposals against what the paper actually says

The CONTEXT frames this reading as evidence for two specific architectural proposals. Grounding them in the survey text (not just the toy demo) matters because the demo alone can't support or refute claims about 72D RL observation vectors, encoders, or domain randomization — none of those concepts appear in it.

**Proposal 1 — lift ALL network inputs (obs + privileged params + proprio history + commands) into one Koopman observable space before encoder+policy.**

The paper is explicit that a Koopman lifting `g(x)` is defined with respect to a specific dynamical system's state-transition map, `x_{t+1}=T(x_t)`, and its accuracy hinges on how close `span(Ψ)` is to being **Koopman-invariant under that map** (p. 1091, Sec. II-B: *"none of the aforementioned convergence results imply that a larger finite-dimensional space is necessarily better for prediction"*; p. 1101, Sec. V-C, Fig. 3, shows a dictionary spanning the identical subspace can have arbitrarily large or near-zero residual error depending on basis choice — invariance is not automatic from adding features). Lifting is a state/observable-space transformation tied to one evolution law, not a generic "make everything more linear" feature transform. Concretely:

- The paper's own taxonomy for lifting-function construction (p. 1094, Sec. III-B) is manually-selected / physics-informed / NN-based dictionaries **of the system state** (and, per Sec. II-C p. 1092, optionally jointly with the *control input* — via one of two named schemes, "joint lifting" or "affine input form"). Privileged environment parameters (hydrodynamic coefficients, currents, thruster faults) are not states that evolve under a step-to-step transition law within an episode — they're fixed-per-episode plant parameters. Nothing in Sections II–III defines lifting for that object; blending them into `phi(x)` has no basis in the reviewed formulations.
- Even the tutorial's own recommended practice for inputs is **not** "lift everything together": the actual EDMD fit used for control (cell 10) sets `include_u_in_phi=False` and instead uses the affine-input form `Φ(x_{t+1}) ≈ K_phi·Φ(x_t) + K_u·u_t` — precisely to *keep* the input separate from the state dictionary, matching the paper's stated preference that affine-input form "aligns naturally with classical control design tools... This formulation has been adopted in many robotic systems" (p. 1092, Sec. II-C-2). The user's proposal to fuse obs+privileged+history+commands into one blanket dictionary is the *opposite* of both the tutorial's and the paper's practice.
- NN-based lifting (the closest analog to "learn a good dictionary automatically," which is what would be needed at 72–100+D) is explicitly flagged with unresolved costs: *"they also introduce challenges, such as interpretability, generalization to out-of-distribution inputs, and the risk of overfitting"* (p. 1094, Sec. III-B-3). Given the UUV project already relies on domain randomization across wide parameter ranges, the OOD-generalization risk named here is directly on point and unaddressed by the survey.

**Verdict on Proposal 1**: unsupported by the paper. The claim that lifting arbitrary heterogeneous inputs (state, privileged params, history, commands) together improves "implicit system identification" has no basis in the surveyed theory or in the tutorial's own design choices, both of which treat state-lifting and input-handling as separate, carefully justified constructs, and both of which flag that lifting-function choice can *fail* to improve linearity without invariance guarantees the paper itself says are hard to establish and unresolved for high-dimensional/soft-robot-scale systems (p. 1103, Sec. VI, "Further expansion on soft robotics": *"lift the system into a high-dimensional space, which can become computationally expensive or even intractable... these approximations inevitably introduce biases and limit generalizability"*).

**Proposal 2 — drop the encoder; Koopman itself does system identification, so no encoder/student distillation is needed.**

The paper does call Koopman estimation "system identification," but a specific and narrow kind: *"[The Koopman operator] facilitates the discovery of the underlying dynamics by estimating the linear operator in real time, which eliminates the need for least-square regression of the nonlinear [transition] function that, in general, requires a large amount of data"* (p. 1090, Sec. II-A). This is fitting a **global dynamics model `K` from a batch/stream of state-transition pairs** (EDMD needs paired `(x_t, x_{t+1})` data, Sec. II-B, Eq. 6-7) — it is not a stateless, single-forward-pass inference of *hidden, per-instance* environment parameters from one observation, which is what the RMA encoder does (map a known privileged-obs vector → 9D latent `z`) and what the TCN/GRU student approximates online from proprioceptive history.

- Every place the paper discusses adapting Koopman models to changing/uncertain dynamics is an **online, iterative re-estimation process requiring new interaction data**, not a single forward pass: the active-learning formulation (p. 1095–1096, Sec. III-C-2, Eqs. 14–16) explicitly optimizes future control inputs to *shrink posterior uncertainty in the operator estimate* via a Fisher-information criterion — i.e., it assumes `K` is *not yet known* and designs data collection to learn it, the opposite of "no learning needed." The disturbance/uncertainty-observer line of work cited (EVOLVER [80], p. 1099; Kalman-filter-augmented Koopman, p. 1096–1097, Sec. III-D) likewise treats unknown dynamics/disturbances as something to be *estimated online*, architecturally closer to the student's recurrent inference than to a stateless lift.
- The paper's own open-problems section says the opposite of "solved, no encoder needed": handling **hybrid/heterogeneous dynamics** (which parameter/fault variation across DR arms effectively is) is called out as "remains open" (p. 1103–1104, Sec. VI, "Extension to hybrid systems"), and the assumption that uncertainty in the lifted operator is well-behaved (e.g., Gaussian) is called "a key direction of future research," explicitly *not* resolved (p. 1104, "Uncertainty in lifted features").
- A single, fixed, offline-fit `K` (exactly what the tutorial produces and what EDMD gives you) is a linear model of **one** dynamical regime. It cannot represent a family of plants varying under domain randomization (different hydrodynamic coefficients, thruster faults) without either being re-estimated online per instance (expensive, not a forward pass) or being extended to a parameter-augmented/family-of-operators form — the paper names such extensions ("Koopman Control Family," p. 1100–1101, Sec. V-B-2) only for **control-input** variation, not for unobserved plant-parameter variation, and even there notes it requires either infinite input-sequence machinery or invariant-subspace assumptions that "in case there is no common invariant subspace... approximate the action... via orthogonal projections" — nontrivial machinery, not a free lunch.
- The one RL-adjacent use case the survey cites (p. 1098, Sec. III-C, soft robots) is Koopman-as-**surrogate training environment** ("bypasses the need for difficult-to-construct physical or simulated soft robot environments... to accelerate policy learning" [67]) — i.e., using a Koopman model to speed up simulation for RL training, not as a substitute for an encoder that infers hidden environment parameters inside the policy's own forward pass. This is a different use of Koopman than the one the proposal invokes.

**Verdict on Proposal 2**: unsupported by the paper, and arguably contradicted by it. "System identification" in the surveyed sense means fitting one linear operator to trajectory data for one dynamical regime — it does not perform the RMA encoder's job (per-episode inference of hidden physical parameters from privileged/proprioceptive signals), and every mechanism in the paper that comes close (active learning, disturbance observers, online re-estimation) requires an online, data-driven adaptation loop that is structurally closer to what the **student's TCN/GRU already does**, not a justification for removing it.
